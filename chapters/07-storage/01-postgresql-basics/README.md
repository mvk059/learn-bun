# 7.1 PostgreSQL Basics

## Overview

Bun includes a built-in PostgreSQL client called `Bun.sql` that provides a fast, ergonomic way to interact with PostgreSQL databases. Unlike traditional query builders or ORMs, Bun.sql uses **tagged template literals** to create parameterized queries that are both safe and readable.

In this lesson you will learn how to:

- Connect to a PostgreSQL database using `Bun.sql`
- Create tables with SQL DDL statements
- Perform full CRUD (Create, Read, Update, Delete) operations
- Use the `RETURNING` clause to get inserted/modified rows back
- Write parameterized queries that prevent SQL injection

## Prerequisites

```bash

```

## Bun.sql Fundamentals

### Creating a Connection

Bun.sql uses the `SQL` class imported from `"bun"`:

```typescript
import { SQL } from "bun";

const sql = new SQL({
  url: "postgres://user:password@localhost:5433/mydb",
});
```

The `SQL` instance manages a connection pool automatically. You do not need to manually acquire or release connections for individual queries.

### Tagged Template Literals

The core feature of Bun.sql is its use of tagged template literals. Instead of building query strings with concatenation (which is dangerous), you write queries like this:

```typescript
const id = "abc-123";
const rows = await sql`SELECT * FROM projects WHERE id = ${id}`;
```

The `${id}` expression is **not** string interpolation. Bun.sql extracts the value and sends it as a parameterized query parameter. This means:

- **No SQL injection** -- values are never embedded directly into the query string
- **Automatic type handling** -- JavaScript types are mapped to PostgreSQL types
- **Clean syntax** -- queries read naturally without placeholder markers like `$1`

### CRUD Operations

#### Create (INSERT)

Use the `RETURNING *` clause to get the inserted row back, including any server-generated values like UUIDs and timestamps:

```typescript
const [project] = await sql`
  INSERT INTO projects (name, description, owner_id, status)
  VALUES (${name}, ${description}, ${ownerId}, ${status})
  RETURNING *
`;
// project.id is now set (generated by the database)
// project.created_at is now set (defaulted by the database)
```

#### Read (SELECT)

Queries return an array of row objects. Property names match column names:

```typescript
// Get all rows
const allProjects = await sql`SELECT * FROM projects`;

// Get one row by ID
const rows = await sql`SELECT * FROM projects WHERE id = ${id}`;
const project = rows[0]; // undefined if not found
```

#### Update (UPDATE)

Combine `UPDATE ... SET` with `RETURNING` to see the modified row:

```typescript
const [updated] = await sql`
  UPDATE projects SET status = ${newStatus} WHERE id = ${id}
  RETURNING *
`;
```

#### Delete (DELETE)

Use `RETURNING` with delete to confirm what was removed:

```typescript
const deleted = await sql`
  DELETE FROM projects WHERE id = ${id}
  RETURNING id
`;
// deleted.length === 0 means nothing was found to delete
```

### Closing the Connection

Always close the SQL connection when you are done, especially in scripts and tests:

```typescript
await sql.close();
```

## Table Design: Projects

For this exercise, you will create a `projects` table with the following schema:

| Column       | Type           | Constraints                        |
| ------------ | -------------- | ---------------------------------- |
| id           | UUID           | PRIMARY KEY, DEFAULT gen_random_uuid() |
| name         | VARCHAR(100)   | NOT NULL                           |
| description  | TEXT           | DEFAULT ''                         |
| owner_id     | VARCHAR(50)    | NOT NULL                           |
| status       | VARCHAR(20)    | DEFAULT 'active'                   |
| created_at   | TIMESTAMPTZ    | DEFAULT NOW()                      |

PostgreSQL's `gen_random_uuid()` function generates a UUID v4 value automatically when a row is inserted.

## Key Takeaways

- `Bun.sql` uses tagged template literals for safe, parameterized queries
- Values embedded with `${}` are never concatenated into the SQL string
- The `RETURNING` clause lets you get back inserted, updated, or deleted rows
- Always close the connection with `sql.close()` when finished
- Use `CREATE TABLE IF NOT EXISTS` for idempotent table creation

## Common Pitfalls

- **Forgetting `RETURNING *`**: Without it, INSERT/UPDATE/DELETE return no row data
- **Not handling empty results**: `rows[0]` is `undefined` when no rows match -- use `?? null` to return `null` explicitly
- **String interpolation vs. tagged templates**: Regular template literals (`` `SELECT * FROM ${table}` ``) do NOT parameterize. You must use the `sql` tagged template
- **Not closing connections**: Leaving connections open can exhaust the connection pool or prevent the process from exiting
