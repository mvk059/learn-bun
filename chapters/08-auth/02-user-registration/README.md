## Introduction

User registration is the gateway to any authenticated application. A well-built
registration system does more than just insert a row into a database. It validates
input, enforces password strength requirements, prevents duplicate accounts, securely
hashes passwords, and returns only the information that is safe to expose.

In this lesson, you will build a `UserService` class that encapsulates all of this
logic. The service pattern keeps your business rules separated from your HTTP layer,
making the code easier to test and reuse.

## The Users Table

Our registration system works against a `users` table with the following schema:

```sql
CREATE TABLE IF NOT EXISTS users (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  username VARCHAR(50) UNIQUE NOT NULL,
  email VARCHAR(255) UNIQUE NOT NULL,
  password_hash TEXT NOT NULL,
  role VARCHAR(20) DEFAULT 'member',
  created_at TIMESTAMPTZ DEFAULT NOW()
);
```

Key details:

- **id**: A UUID generated by PostgreSQL, not an auto-incrementing integer.
- **username** and **email**: Both have `UNIQUE` constraints. Attempting to insert a
  duplicate will cause a database error that we must handle gracefully.
- **password_hash**: Stores the Argon2id hash, never the plaintext password.
- **role**: Defaults to `"member"`. Roles will matter more in later lessons on
  authorization.

## Password Strength Validation

Before hashing, you should verify the password meets minimum strength requirements.
A common baseline:

| Rule                    | Reason                              |
|-------------------------|-------------------------------------|
| At least 8 characters   | Short passwords are easily brute-forced |
| Contains uppercase letter | Increases character space           |
| Contains lowercase letter | Increases character space           |
| Contains a digit        | Increases character space           |

```typescript
function validatePasswordStrength(password: string): string[] {
  const errors: string[] = [];
  if (password.length < 8) errors.push("Password must be at least 8 characters");
  if (!/[A-Z]/.test(password)) errors.push("Must contain uppercase letter");
  if (!/[a-z]/.test(password)) errors.push("Must contain lowercase letter");
  if (!/[0-9]/.test(password)) errors.push("Must contain a number");
  return errors;
}
```

Returning an array of error messages lets the caller know exactly what failed. If the
array is empty, the password is acceptable.

## Handling Unique Constraint Violations

When a user tries to register with a username or email that already exists, you have
two approaches:

1. **Check first, then insert** -- Query the database to see if the username or email
   exists before attempting the insert. This is simpler to reason about and produces
   clear, specific error messages ("Username already taken" vs. "Email already
   registered").

2. **Insert and catch the constraint error** -- Attempt the insert and catch the
   PostgreSQL unique violation error (code `23505`). This avoids a race condition but
   makes it harder to distinguish which field caused the conflict.

In this lesson we use approach 1 for clarity.

## The SafeUser Type

Never return the password hash to the client. Define a `SafeUser` interface that
includes only the fields that are safe to expose:

```typescript
interface SafeUser {
  id: string;
  username: string;
  email: string;
  role: string;
  createdAt: Date;
}
```

After inserting the user, map the database row to this shape. The `password_hash`
column is excluded by selecting only the columns you need in the `RETURNING` clause:

```sql
INSERT INTO users (username, email, password_hash)
VALUES ($1, $2, $3)
RETURNING id, username, email, role, created_at
```

## Custom HTTP Errors

To communicate specific HTTP status codes from your service layer, create a custom
error class:

```typescript
class HttpError extends Error {
  statusCode: number;
  constructor(statusCode: number, message: string) {
    super(message);
    this.statusCode = statusCode;
  }
}
```

- **400** for validation failures (weak password, missing fields)
- **409** for conflicts (duplicate username or email)

This pattern lets your HTTP handler catch `HttpError` instances and set the response
status code accordingly, without coupling the service to any web framework.

## Hashing with Bun.password

Bun provides a built-in `Bun.password.hash` function that supports Argon2id:

```typescript
const passwordHash = await Bun.password.hash(input.password, {
  algorithm: "argon2id",
});
```

The returned string includes the algorithm identifier, salt, and hash parameters, so
you can later verify passwords with `Bun.password.verify` without storing anything
extra.

## Registration Flow Summary

1. Validate password strength. Throw 400 if too weak.
2. Check if the username is taken. Throw 409 if it exists.
3. Check if the email is taken. Throw 409 if it exists.
4. Hash the password with Argon2id.
5. Insert the new user into the database.
6. Return a `SafeUser` object (no password hash).

## Key Takeaways

- Always validate input before doing any database work.
- Hash passwords with a strong algorithm (Argon2id) before storing them.
- Handle unique constraint violations with clear, specific error messages.
- Never expose password hashes in API responses -- use a safe projection type.
- Custom error classes with status codes keep your service layer decoupled from HTTP.
